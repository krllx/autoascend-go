### 1.2 Как устроен один шаг сейчас

Бот написан "тянущим" стилем, как в Python: агент живет в своей горутине и сам зовет `a.Step(action)` из глубины вложенных функций.

```
aabot: читает obs -> Driver.Act(obs) --канал--> горутина агента была заблокирована в env.Step()
  env.Step() возвращает obs -> a.update(obs):
     разобрать сообщение/попап; если --More-- / меню / [yn] / итератор клавиш -> еще a.Step(...) (рекурсия)
     иначе UpdateState(): Character, Inventory, MonsterTracker, CheckTerrain, UpdateLevel, GlobalLogic
        (часть из них сама жмет клавиши: ':' под собой, '#terrain', ';' монстры, '\' известные, осмотр контейнеров)
     затем колбэки on_update: проверки всех активных Preempt; сработавшая -> panic(AgentChangeStrategy)
  управление возвращается в функцию, которая звала Step, она решает следующее действие -> a.Step(next)
  --канал--> Act возвращает индекс действия
```

Типичный стек в момент шага: `Main -> Try -> GlobalStrategy (9 слоев Preempt) -> Repeat -> currentStrategy (цикл по вехам) -> GoToLevelStrategy -> Preempt -> explorationStrategy -> Explore1 -> GoTo -> MoveTo -> Direction -> Step -> update -> Step(--More--) -> ...`

### 1.3 Где живет состояние

Явное (структуры, сериализуется напрямую): `Agent` (blstats, счетчики, сообщения, история), `Levels` (карты уровней), `Inventory`/`InventoryItems`/`ItemManager` (предметы и знание о них), `Character`, `MonsterTracker`, `GlobalLogic` (веха, уровни оракула и Minetown), `Rng` (MT19937: 624 слова + позиция).

Скрытое (не сериализуется, это и надо убрать):

1. **Стек горутины агента** - где бот сейчас внутри вложенных процедур и их локальные переменные (счетчики циклов, цели, списки).
2. **Замыкания стратегий**: захваченные переменные тел (`trapLocations`, `target`...), счетчики `Every(n)`, условия `Condition/Until`, колбэк `GoToOpts.Callback`, фабрики `goToStrategy` / `explorationStrategy`.
3. **`onUpdate`** - список замыканий-проверок после каждого шага (проверки Preempt, `PanicIfPositionChanges`, `PanicIfItemsBelowMeChange`).
4. **Сопрограммы `iter.Pull`** - 13 "ленивых" генераторов клавиш (`StepGen`: Elbereth, выбор в меню подбора, #enhance...).
5. **Управление через panic**: `AgentChangeStrategy` несет продолжение-замыкание и раскручивает стек до своего Preempt; `AgentPanic` раскручивает до `Main`, тот делает `OnPanic` и перезапускает `GlobalStrategy`.
6. **defer-уборка**: `AtomOperation` (флаги атомарной операции; `UpdateState` только при нормальном выходе), `DisallowStepCalling`, снятие колбэков.
7. **Глобальные переменные**: кэши чистых функций (`parseTextCache`, кэш `ParseName`, `unionCache`) и отладочный `panicSite`. На поведение не влияют.
8. **Драйвер**: горутина, каналы, таймер.

Масштаб (граф вызовов по `go/types`): из 486 функций до `Step` прямо или косвенно доходят 98, это ~4100 строк. Их придется переписать в явные автоматы. Остальные ~8,5 тыс. строк - чистые вычисления, переносятся почти как есть.

### 1.4 Тонкие места, которые нельзя сломать

- **Семантика Preempt.** После каждого завершенного шага вне атомарной операции проверки идут в порядке регистрации (внешние слои первыми). Сработавшая: все, что ниже ее Preempt, выбрасывается, исполняется тело прерывающей стратегии, затем (если `continue`) нижний слой **перезапускается с нуля**, а не продолжается. Пока идет тело прерывателя, проверки его соседей по слою сняты. При входе в Preempt проверки зовутся один раз сразу. Проверки не жмут клавиши, но меняют состояние: `Every` считает вызовы, `offerCorpses` ставит `TakeSacrificialCorpses`.
- **Моменты создания узлов.** Счетчики `Every` живут в экземпляре. `GlobalStrategy()` строится заново после каждого `AgentPanic`, дерево вехи - на каждой итерации цикла, `exploreStrategy` в `GoToLevelStrategy` переиспользуется между итерациями. Новые узлы должны создаваться ровно в те же моменты.
- **Атомарная операция**: внутри нее нет полного обновления и нет проверок; на нормальном выходе - `UpdateState(true, true)`, на исключении - нет.
- **Вложенный порядок в `update`**: ответ `y` на `[yn]` идет через `TypeText` = атомарная операция, и полное обновление делает ее выход, а не внешний шаг.
- **Сид 1061**: бесконечный цикл без шагов, драйвер дважды ждет 118 с, дальше только ESC.
- Буферы obs не переиспользовать (старые кадры держат свои obs).

## 2. Цель

### 2.1 Главная идея: стек вызовов становится данными

Каждая многошаговая процедура становится **кадром** (frame): структурой, в которой лежат ее локальные переменные и номер места, где она остановилась (`PC`). Вместо стека горутины - явный срез кадров `[]Frame` в состоянии бота. Кадр не жмет клавиши сам и не ждет: он говорит машине, что делать дальше, - "запусти дочернюю процедуру", "я закончил, вот результат" (а самый нижний, шаг ввода-вывода, - "отдай клавишу игре"). Машина кладет и снимает кадры. Весь бот - это `World` (данные о мире) + `Machine` (стек кадров, список проверок, флаги атомарной операции). Снимок = сериализация этих двух структур.

Стратегия Python (генератор с одним `yield`) делится на две части:
- `Check` - код до `yield`: чистая проверка "применима ли сейчас", возвращает `ok` и **кадр тела** с уже вычисленными данными (цель, список ловушек). Это и есть "тактика предлагает, но не жмет".
- тело после `yield` - кадр с полями вместо захваченных переменных.

Исключения внутри одного `Resume` остаются Go-паниками (`Assert/Panic/Raise` не меняются). Машина ловит их на границе кадра и раскручивает явный стек, вызывая у кадров уборку (`Finally`) и обработчики (`Catch`), - так же, как сейчас это делают defer и `Try`. Фатальные ошибки (Assert, runtime) по-прежнему роняют бота в режим "только ESC".

Пример (`UntrapTraps`, `explore.go`):

```go
// было: тело - замыкание, держит trapLocations, level, trapMask в захваченных переменных
return true, func() any {
    t := trapMask.Nonzero()[0]
    a.GoTo(t.Y, t.X, GoToOpts{})
    for _, tl := range trapLocations {
        if Adjacent(me, tl) { ...проверки, Panic...; a.Untrap(tl.Y, tl.X); a.CheckTerrain(true) }
    }
    return nil
}

// стало: tactics/untrap_traps.go
type UntrapTraps struct{} // узел без состояния; Check - прежний код до yield, без изменений
func (UntrapTraps) Check(c *engine.Ctx) (bool, engine.Frame) {
    ...
    return true, &untrapBody{Level: level, Target: trapMask.Nonzero()[0], Traps: trapLocations}
}

type untrapBody struct {
    Level  *world.Level // тот же объект уровня, что захватывал Python
    Target grid.Pos
    Traps  []grid.Pos
    I, PC  int          // какая ловушка и где остановились
}

func (s *untrapBody) Resume(c *engine.Ctx) engine.Cmd {
    switch s.PC {
    case 0: // дойти до клетки рядом с ловушкой
        s.PC = 1
        return engine.Call(skills.GoTo(s.Target, skills.GoToOpts{}))
    case 2: // Untrap закончился - проверить местность
        s.PC = 3
        return engine.Call(sense.CheckTerrain(true))
    case 3:
        s.I++
    }
    for ; s.I < len(s.Traps); s.I++ { // PC 1: перебор ловушек
        tl := s.Traps[s.I]
        if !grid.Adjacent(c.W.Me(), tl) { continue }
        ... // те же проверки и Panic
        if tl == c.W.Me() { continue }
        s.PC = 2
        return engine.Call(skills.Untrap(tl))
    }
    return engine.Return(nil)
}
```

Правила (закрепляются тестом `deps_test.go` по `go list -deps`):
- `skills`, `tactics`, `strategy` не импортируют `io`, `brain`, `snapshot`; клавиши - только через `engine.Cmd`.

### 2.3 Ключевые интерфейсы

```go
package engine

// Frame - незаконченная многошаговая процедура. Только данные: без func, chan, указателей внутрь чужих структур.
type Frame interface{ Resume(c *Ctx) Cmd }

type Ctx struct {
    W   *world.World
    M   *Machine
    Ret any // результат дочернего кадра, если он только что закончился
}

func Call(f Frame) Cmd      // запустить дочернюю процедуру
func Return(v any) Cmd      // закончить
func Send(a nle.Action) Cmd // только кадр шага из io: отдать клавишу и ждать obs

// Необязательно:
type Finalizer interface{ Finally(c *Ctx, normal bool) }       // defer / finally
type Catcher interface{ Catch(c *Ctx, e *Unwind) (handled bool) } // try / except
type Watcher interface{ Watch(c *Ctx, i int) (fire bool, body Frame) } // i-я проверка on_update этого кадра

// Node - стратегия AutoAscend. Check - код генератора до yield: клавиш не жмет.
type Node interface{ Check(c *Ctx) (ok bool, body Frame) }
type Pred interface{ Eval(c *Ctx) bool } // условия как данные: XPAtLeast{8}, NotHungry{}, AtPos{y, x}...

type Machine struct {
    Stack    []Frame
    OnUpdate []WatchRef // проверки после шага в порядке регистрации, как список on_update в Python
    Atom     AtomState  // turns_in_atom_operation, allow_update
    NoStep   bool       // disallow_step_calling
    NextID   int
    Dead     string     // бот упал: дальше только ESC
}
```

Шаг бота: `brain.Act(st, obs)`: машина отдает obs верхнему кадру (кадру шага из `io`) и крутит `Resume` до следующего `Send`. Состояние меняется на месте; "чистая функция (State, Obs) -> (State', Action)" получается через `snapshot.Clone` там, где нужна (копировать мегабайты на каждом шаге дорого).

Навыки: предусловия - `Assert` в начале, как сейчас. "Можно ли прервать" - это не свойство навыка, а атомарная операция: внутри `engine.Atom(...)` проверок нет, как в Python.

### 2.4 Стратегия как данные

Слои `GlobalStrategy` - таблица (снизу вверх; каждый следующий прерывает все, что ниже):

```go
func globalLayers() [][]engine.Node {

        {tactics.WaitOutUnexpectedState{}},

        {tactics.Fight{}},
```

Вехи - таблица `{веха, условие завершения (Pred), целевой уровень}` вместо `switch` в `currentStrategy`. Функция, а не `var`: узлы с `Every` должны создаваться заново там же, где сейчас.

### 2.5 Снимок

- Свой кодек на `reflect`: сохраняет указатели и их общность (один `*Item` в инвентаре и в `MainHand` после загрузки остается одним объектом - от этого зависит логика), циклы, неэкспортированные поля, интерфейсы (реестр типов кадров и узлов), массивы примитивов копирует блоком. Указатели на статичные таблицы (`*Obj`, `*Permonst`, `*GSet`) пишет как индексы. `gob` не подходит: он теряет общность указателей и не видит неэкспортированных полей.
- Кодек отказывается писать `func`, `chan`, указатели внутрь структур. Отсюда тест "в состоянии нет замыканий": снимок каждого из 49 сидов в сотне точек.
- В снимок входят `World` (с RNG и последними obs), `Machine`, состояние драйвера. Кэши чистых функций - нет (они прозрачны).
- Оценка: 0,5-2 МБ до сжатия (уровень ~50 КБ: 11 карт по 1659 клеток), 50-150 КБ в gzip, 1-5 мс на снятие.

### 2.6 Детерминизм и прочие правила (тоже тестами)

- AST-проверка: нет `range` по Go `map`, нет `go`/`chan`/`select` вне `cmd`, нет изменяемых глобалов кроме списка кэшей.
- Время и случайность - только через `World` (RNG там).
- Зависание без шагов (сид 1061): бюджет операций машины без `Send`. Превышен -> бот считается упавшим и шлет ESC; поток действий тот же, что сейчас, только без 2 x 118 с. Сторожевой таймаут остается только в `cmd/aabot` как страховка.
- Файл до ~300-400 строк, один навык или тактика на файл.

## 3. План переноса (strangler снизу вверх)

Переписанная процедура может звать только уже переписанные, поэтому идем от листьев графа вызовов к `Main`. Пока верх не переписан, горутина остается, а кадры крутятся внутри нее: `engine.Machine.Run` в режиме с `Env` шлет клавиши через канал старого драйвера, а исключения старого кода пролетают сквозь кадры. После каждого шага: `GOARCH=amd64 go test ./...` (корпус 48 сидов), коммит; на blackbox - 49 сидов `baseA` и разностный прогон на новых сидах.

Порядок изменен против первой версии плана (30.09): раскладка по `world/skills/tactics/strategy` - в конце, а не вторым шагом. У `Inventory`, `ItemManager`, `Character` методы с клавишами перемешаны с чистыми, и Go не дает оставить их в `aa`, пока тип живет в `world`: пришлось бы дважды переписывать сигнатуры ~100 функций. Итоговая архитектура та же.

2. **Go 1.27 и PGO.** В 1.27 ускорили мелкие аллокации (по заметкам к релизу ~1% в программах, которые много выделяют). PGO дал -3% CPU бота. Профиль снимать с нового кода (`AABOT_CPUPROFILE`) и хранить как `cmd/aabot/default.pgo`. После смены тулчейна - полная сверка.
3. **Маски карты битами и SIMD для разведки.** `BoolGrid` как 21 строка x 2 слова `uint64`: And/Or/Not/Any/Count и подсчет соседей идут по 64 клетки за операцию, SIMD для этого не нужен. SIMD (Go 1.26+ `simd/archsimd`, в 1.27 еще переносимый `simd`; оба под `GOEXPERIMENT=simd`, API нестабилен) - для однородных float32-проходов разведки. Поэлементные операции в векторе дают те же биты, что и по одной, если нет FMA. Не подходят: BFS (очередь, нерегулярные переходы) и выборки из таблицы глифов в `UpdateLevel`. Оценка без замера: 10-20% CPU бота.
4. **Инкрементальное обновление карты.** Пересчитывать только клетки, где глиф изменился с прошлого шага: разведка, `UpdateLevel`, трекер монстров. Самый большой потенциал и самая трудная сверка: надо сохранить порядок float32-вычислений.

Условия:

- **Где живет быстрый код.** SIMD, битовые трюки и инкрементальные кэши - только в утилитных пакетах (`grid`, внутренности `perception`/`sense`), за обычными функциями с понятными именами (`NeighborCount8`, `BFS`, `Isin`, операции над масками). Слои, в которых меняется поведение бота (`tactics`, `strategy`, `brain`, боевые эвристики, приоритеты предметов), остаются простым Go и только зовут эти функции. Поиск пути и учет карты - стабильные алгоритмы без "интеллекта", при правках поведения их менять и читать не нужно.
- **`GOAMD64=v3` нельзя:** компилятор начнет сливать a*b+c в FMA по всему коду, и округление разойдется с Python. SIMD - только явными вызовами пакета, с проверкой возможностей процессора и скалярной веткой: какой процессор у машины проверки NetHackers, неизвестно.
- **Экспериментальный API:** версию Go зафиксировать в `go.mod` (`toolchain`).
- **Каждая оптимизация - отдельный коммит** с полной сверкой (корпус и blackbox `baseA`) и замером до и после в одинаковых условиях: прогоны вперемешку, скорость blackbox плавает до 1.7x.

### 7.1 Падения AutoAscend после `v1`

Каждая правка - отдельный коммит. Проверка: 49 сидов `baseA` и 300 новых сидов 3000-3299 на blackbox, полные партии с `--ref` на трассы предыдущей правки (для первой - `v1`/`seeds_v1`) и `--dump`; "до" - прогон предыдущей правки. Сиды корпуса, партия которых меняется, перезаписаны ботом с правкой (локальный корпус, в git его нет).

- Тяжелое ядро (наказание). Причина: у ядра и цепи нет описания, а класс BALL стоял только среди префиксов описаний, поэтому `heavy iron ball` разбиралось как `unknown` (категория VENOM), и проверка категории в разделе "Iron balls" меню подбора падала. Вторая причина: когда на клетке лежат цепь и ядро, `:` показывает два предмета, бот жмет `,`, а игра без меню берет единственный предмет кроме цепи - спрашивает "You have a little trouble lifting ... Continue? [ynq]" или сразу берет ("J - a heavy iron ball (chained to you)."), и `lookBelowF` падал на незнакомом сообщении. Правка: ядро и цепь разбираются по имени (BALL и CHAIN в префиксах и суффиксах имен); после `,` без меню бот отвечает `n` на вопрос о тяжести и считает, что под ним этот один предмет (буква None, как после "You see here"), а если предмет уже взят - что под ним пусто. Меняются: из 49 сидов 1084 и 1086, из 300 новых 3022, 3120, 3216, 3294; все шесть вместо ESC до конца доигрывают до настоящей смерти (голод, шакал, летучая мышь, элементаль), прогресс и глубина те же. Средний прогресс: 49 сидов 0.07897 -> 0.07897, 300 сидов 0.04991 -> 0.04991. В корпусе перезаписаны 1084 и 1086.
- Ботинки в капкане (`turn inactivity`, 1136). Причина: агент стоит в медвежьем капкане, подобрал ботинки и пытается их надеть; игра отвечает "Your foot is trapped!" без хода, `wear_best_stuff` повторяет попытку, пока проверка "turn inactivity" (200 шагов без хода) не роняет бота. Правка: отказ надеть или снять ботинки из-за ног (капкан, застрял в полу, закопанное ядро) запоминается в `Agent.FeetStuckTurn`, и до конца этого хода слот ботинок пропускается; бот идет дальше и выбирается из капкана. Меняется только 1136 (из 49): доигрывает до смерти (owlbear) на Dlvl 6 вместо ESC на Dlvl 2, прогресс тот же (0.07454). Средний прогресс не изменился (0.07897 и 0.04991). В корпусе перезаписан 1136.
- Вопрос "eat it?" про названный труп (`turn inactivity`, 3011). Причина: бот сам называет старые трупы (`#old`), а шаблон "There is ... here; eat it?" допускал в названии предмета только буквы, цифры, `-` и пробел; вопрос не узнавался, буква предмета из инвентаря уходила в `[ynq]`, еда повторялась без хода. Правка: в названии допустимо все, кроме `;`. Меняется только 3011 (из 300): прогресс 0.02911 -> 0.05076, доигрывает до смерти (hill orc) на Dlvl 1 вместо ESC. Средний прогресс по 300: 0.04991 -> 0.04998, по 49 тот же.
- Бросок при перегрузе (`turn inactivity`, 3166). Причина: при Overtaxed и тяжелее игра отказывает в броске и взмахе палочкой ("You can't do that while carrying so much stuff.") без хода, а буква предмета уходит дальше как команда: в 3166 `w` вооружил бота зельем, и бой повторялся до "turn inactivity"; в других партиях буква закрывала двери и т.п. Правка: при нагрузке Overtaxed и выше `fight2` не выбирает действия `ranged` и `zap` (фильтр после выбора возможных действий, как для полиморфа, чтобы остальной выбор не менялся); в `useItemDirF` такой отказ дает `AgentPanic`, а не букву-команду. Меняются 4 из 300: 3166 (доигрывает до смерти вместо ESC), 3068, 3187, 3296 (там бросок при перегрузе тоже был, но без зацикливания); прогресс у всех четырех тот же. Средний прогресс не изменился (0.07897 и 0.04998).
- Второй труп из старого списка (`TODO: nested containers`, 1123). Причина: `eat_corpses_from_ground` ест все подходящие трупы из списка предметов под агентом, снятого до еды; после первого трупа список заменяется новыми объектами, следующий старый труп не лежит ни под агентом, ни в инвентаре, и `move_to_inventory` падает. Правка: из старого списка едятся только предметы, которые все еще в текущем списке; следующий труп съест следующая проверка тактики, если агент еще не сыт. Меняется только 1123 (из 49): прогресс 0.05076 -> 0.11705, Dlvl 1 -> 5, смерть от обезьяны вместо ESC. Средний прогресс по 49: 0.07897 -> 0.08032, по 300 тот же. В корпусе перезаписан 1123.
- Сокращенные состояния в строке статуса (`All monsters currently shown on the map: is not in list`, 3128). Причина: когда нижняя строка не помещается, tty сокращает состояния (`Hungry Stun Cnf Hal`: Conf -> Cnf -> Cf, Hallu -> Hal -> Hl, Blind -> Blnd -> Bl, Stun -> St), а бот искал только полные слова; галлюцинация не распознавалась, бот слал `M` в меню `;`, где при галлюцинации такого пункта нет. Правка: `Property.statusHas` принимает и короткие формы - целыми словами после поля времени `T:`. Меняются: из 49 сидов 1029 (слепота как `Blnd`, смерть от owlbear вместо белого единорога, прогресс тот же 0.11705); из 300 новых 3128 (доигрывает до смерти вместо ESC, прогресс тот же) и 3141 (прогресс тот же). Средний прогресс не изменился (0.08032 и 0.04998). В корпусе перезаписан 1029.
- Сообщение об убийстве (`rmor catches fire and burns`, 3135). Причина: в шаблоне "kills/destroys (a|an|the) <имя>!" у артикля `(an?)` не было пробела, и "Your scroll of destroy armor catches fire and burns!" дало имя "rmor catches fire and burns", а "kill a newt!" дало бы " newt"; поиск монстра по такому имени падал. Правка: артикль забирает свой пробел, а имя, которого нет среди монстров (`MON_IsName`), пропускается; раньше оба случая падали одинаково. Меняется только 3135 (из 300): доигрывает до смерти вместо ESC, прогресс тот же (0.07454). Средний прогресс не изменился.
- Монстр прячется под предметом (1069). Причина: строка списка `;` для прячущегося монстра называет предмет ("garter snake, hiding under a scroll labeled NR 9"), а шаблон строки допускал в описании только буквы и `-,' `. Правка: описание - любой текст (из него берется только слово "peaceful"). Меняется только 1069 (из 49): доигрывает до шага 77700 и смерти от rothe вместо ESC с шага 38003, прогресс тот же (0.07454). Средний прогресс не изменился. В корпусе перезаписан 1069.
- Длинное сообщение с переносом (`Message doesn't match the screen`, 3066). Причина: сообщение длиннее строки (прочитанная надпись на полу) tty переносит поверх карты и пишет там только свои символы; во второй строке осталась карта, кроме последнего столбца, и строки экрана не складываются в сообщение. Правка: если первая строка начинает сообщение, а текст перед `--More--` его заканчивает, экран - это одно сообщение без всплывающего окна. Меняется только 3066 (из 300): прогресс 0.02911 -> 0.03689, Dlvl 1 -> 3, смерть вместо ESC. Средний прогресс по 300: 0.04998 -> 0.05001.
- Страж хранилища вне досягаемости (`no reachable neighbor`, 3031). Причина: агент в хранилище, коридор стража выходит из него по диагонали между двумя стенами, а бот несет больше 600 (игра такой проход тоже не дает, BFS бота его не строит); `follow_guard` звал `go_to` с `stop_one_before`, и тот падал, не найдя достижимой соседней клетки. Правка: если ни страж, ни его соседи недостижимы, `FollowGuard` не срабатывает. Проверка не должна менять то, что увидит `go_to`: соседи берутся без перемешивания (оно тянет случайное состояние; первая версия правки с перемешиванием поменяла еще 4 партии со стражем) и BFS без записи в кэш шага (`Agent.BfsPeek`). Меняется только 3031 (из 300), ровно на шаге падения: прогресс 0.05076 -> 0.11705, Dlvl 1 -> 3, смерть от голода вместо ESC. Средний прогресс по 300: 0.05001 -> 0.05023.
- Вечный цикл в `eat` без клавиш (найден чтением кода, в партиях не встречался). Причина: в ветке, где еда лежит под агентом, цикл по вопросам "eat it? [ynq]" не отвечал `n` на чужой предмет и не менял сообщение, так что крутился внутри одного кадра, пока его не остановит сторожевой таймер aabot (118 с); на свой предмет вызывал несуществующий `Inventory.type_text` (AttributeError). Правка: цикл стал кадром - `y` на свой предмет (и еда сделана), `n` на чужой и следующий вопрос. Партии не меняются: 0 из 49 и 0 из 300 (ветка практически недостижима: предмет из инвентаря должен после `e` оказаться в списке под агентом).
